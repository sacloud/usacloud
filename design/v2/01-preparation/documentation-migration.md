# 公式マニュアルへのドキュメント移管

## 目的

現在の usacloud ドキュメントは
[`docs.usacloud.jp/usacloud/`](https://docs.usacloud.jp/usacloud/) で公開している。
内容は usacloud の利用に必要な情報を一通り含んでいるが、さくらインターネットの
サービスマニュアルとはドメイン、ナビゲーション、検索が分かれている。

usacloud を公式ツールとして見つけやすくし、API や各サービスのマニュアルと続けて
参照できるよう、利用者向けドキュメントの正規の公開先を
[`manual.sakura.ad.jp`](https://manual.sakura.ad.jp/) へ移す。

移管後は次の状態を目指す。

- 「さくらのクラウド」のマニュアル内で、コントロールパネル、API、CLI の情報を
  横断して探せる。
- インストールから最初のリソース操作までを、外部サイトへ移動せず完了できる。
- 代表的な操作を実環境で動作確認し、その結果に基づくチュートリアルを提供する。
- コマンドの詳細な仕様は CLI の help で確認でき、マニュアルからもその調べ方が
  分かる。
- 旧サイトの全ページから、新しい公式マニュアルへ到達できる。

## 調査結果

### 現在の公開状態

`manual.sakura.ad.jp` には、すでに
[「さくらのクラウド > ツール > usacloud」](https://manual.sakura.ad.jp/cloud/tool/usacloud/index.html)
が存在する。2026 年 4 月 8 日更新のページでは usacloud を公式 CLI クライアントと
説明しているが、本文は `docs.usacloud.jp` への案内だけである。

現在の本文は
[`sacloud/docs.usacloud.jp`](https://github.com/sacloud/docs.usacloud.jp) の
`src/usacloud/` で管理されている。MkDocs のナビゲーションは大きく次の構成である。

- 導入ガイド
- 基本的な使い方
- クエリ、シェル補完、`rest` のガイド
- バージョンアップガイド
- グローバルオプション、プロファイル、環境変数
- リソースごとのコマンドリファレンス

2026 年 8 月時点で `src/usacloud/` には 74 ファイル、うち 62 の Markdown ページが
ある。Markdown ページの内訳は導入、利用、アップグレード等が 8 ページ、
リファレンスが 54 ページである。リファレンスを usacloud のコードから生成する
`tools/gen-command-reference.go` もあるが、現在の生成処理は古い usacloud の
パッケージ構成に依存しており、最新 CLI と常に同期する仕組みにはなっていない。
また、これらのページは CLI の help をほぼそのまま掲載する構成であり、公式
マニュアルへ同じ形で移す意義は小さい。

公開は GitHub Actions から `gh-pages` ブランチへ行われている。旧サイトは共通の
MkDocs テーマで生成されているため、全ページに移管先への案内を表示できる。

### 移管先について

`manual.sakura.ad.jp/cloud/` は Sphinx で構成されている。
usacloud では、このうち初回利用と実際の運用手順を中心に記述する。

## 基本方針

### 実環境で確認したチュートリアルを中心にする

公式マニュアルは次の内容に絞る。

| 種別 | 目的 | 更新方法 |
|---|---|---|
| チュートリアル | 実際の利用目的を、準備から結果確認、後片付けまで通して説明する | 安定版 CLI を実環境で実行して執筆、レビューする |
| 基本概念 | profile、ゾーン、リソース指定、出力など複数の操作に共通する考え方を説明する | CLI の挙動変更時に更新する |
| アップグレード | 非互換変更と設定の移行方法を説明する | リリース前に動作確認して更新する |

コマンド名、Usage、引数、フラグ、enum の網羅的な説明は CLI の `--help` を正とし、
そのままマニュアルへ転載しない。help の改善は CLI 側で行う。マニュアルには
「どのコマンドを、どの順序で、なぜ実行するか」と、実行した結果どうなったかを載せる。

チュートリアルのコマンド例は机上で作らず、専用の検証環境で最初から最後まで実行する。
一部のコマンドだけが動くことではなく、記載した前提条件、作成、状態確認、後片付けまで
一連の手順が再現できることを確認する。

## 推奨する章立て

### 1. usacloud について

- usacloud でできること
- 対応するサービスと対象バージョン
- コントロールパネル、API、Terraform との使い分け
- GitHub リポジトリ、ライセンス、サポート範囲

最初のページだけで「さくらのクラウド公式 CLI」であること、対象となる製品、
次に読む導入ガイドを判断できるようにする。

### 2. クイックスタート

1. 動作環境を確認する。
2. OS ごとの方法でインストールする。
3. API キーを作成し、認証情報を設定する。
4. 接続状態を確認する。
5. リソースを一覧表示する。
6. サンプルで作成したリソースがある場合は削除する。

インストール方法はシェルスクリプト、Homebrew、Windows、バイナリ、
コンテナイメージに分ける。API キーの作成自体は既存の
[API キーマニュアル](https://manual.sakura.ad.jp/cloud/api/apikey.html) を正とし、
同じ手順を重複させない。

v2 で `auth login` を提供した後は、クイックスタートの標準手順を
`auth login` に切り替える。アクセストークンやシークレットをコマンドライン引数へ
書く例は掲載しない。

### 3. 基本概念

- コマンドの構文と、サービス、リソース、アクションの関係
- IaaS の短縮形と `<service>-api`、高レベルコマンドの使い分け
- ID、名前、タグによるリソース指定と一致条件
- リージョンとゾーン、`--zone=all`
- profile と認証情報
- 同期実行、待機、`--no-wait`
- 破壊的操作の確認と `--assumeyes`

コマンド体系の変更時に導入ガイド全体を書き直さずに済むよう、概念説明を独立させる。

### 4. 出力と自動化

- table、JSON、YAML の選択
- ID のみの出力
- JMESPath と jq によるクエリ
- Go template による整形
- `--parameters` と skeleton/example の利用
- 終了コードとエラー処理
- 環境変数、CI/CD、非対話実行
- シェル補完

コピー可能な例には、必要なゾーンや profile を明示する。秘密情報を引数へ埋め込む例、
実在する ID やトークンに見える例は使わない。

### 5. 目的別チュートリアル

コマンド名ではなく、利用者が達成したい作業を見出しにする。

- サーバーを作成し、起動、接続、削除する
- ディスクを追加、交換、バックアップする
- スイッチとルータを構成する
- 複数ゾーンのリソースを確認する
- Web Accelerator など IaaS 以外のサービスを操作する
- `rest` で未対応 API を呼び出す
- 定期処理や CI/CD から安全に実行する

サービス自体の仕様、料金、制限は各サービスのマニュアルを正とし、usacloud 側では
CLI 固有の操作だけを説明して相互リンクする。各サービスのマニュアルからも
「CLI で操作する」導線を設ける。

チュートリアルは小さな操作ごとに分断せず、利用者が一つの目的を完了できる単位にする。
例えばサーバー作成では、plan や archive の検索、サーバーとディスクの作成、起動、
接続確認、削除までを一つの流れとして扱う。

### 6. コマンドの調べ方

コマンド仕様を転載する代わりに、CLI 自身から正確な情報を得る方法を説明する。

- `usacloud --help` でサービスやリソースを探す。
- `usacloud <resource> --help` で利用可能な action を確認する。
- `usacloud <resource> <action> --help` で引数、フラグ、enum、使用例を確認する。
- `--example` や skeleton からパラメータファイルを作る。
- 高レベルコマンドと `<service>-api` のどちらを使うか判断する。

この章には help の長い出力を固定して載せない。短い抜粋が必要な場合も、説明対象の
箇所だけに限定する。すべてのフラグを一覧したオンラインリファレンスは作らず、
CLI のバージョンと help が常に一致することを優先する。

### 7. アップグレード

- サポートするバージョンと確認方法
- v1 から v2 への移行
- `usacloud` から `skr` へのコマンド名変更
- 非互換変更、非推奨機能、削除予定
- 設定ファイルと profile の移行

最新版の説明に過去バージョンの注記を混在させず、移行に必要な情報をこの章へ集約する。

## チュートリアルの標準構成

目的別チュートリアルは原則として次の順で書く。

1. このページで行うこと
2. 前提条件
3. 操作手順
4. 実行結果の確認
5. 作成したリソースの後片付け
6. 注意事項とトラブルシューティング
7. 関連するサービスマニュアルと help の確認方法

破壊的操作、有償リソース、停止を伴う操作は、実行手順より前に注意を置く。

### チュートリアルの記載事項

各チュートリアルには次を含める。

- 動作確認した usacloud のバージョンと確認日(これはコメントに書いておけば良さそう)
- 利用したサービス、ゾーン、必要な権限
- 作成されるリソースと料金が発生する範囲
- コピーして実行できるコマンド
- 各操作の目的と、期待する状態
- 実行結果を確認するコマンドと、確認すべき出力
- 失敗しやすい箇所と対処方法
- 作成したリソースを確実に削除する手順

実行結果の全文を固定値として掲載する必要はない。ID、IP アドレス、日時など
実行ごとに変わる値はプレースホルダーに置き換え、利用者が確認すべきフィールドと
状態が分かる形にする。

トークン、シークレット、アカウント情報などが記載されないように留意する。

### 検証環境

チュートリアルの確認には検証プロジェクトと API キーを使う。
検証は AI を利用して実施し、マニュアルのプロトタイプの記述まで AI で実施できるように SKILL を整理しておく。

### 更新タイミング

- 安定版リリースごとに主要チュートリアルの検証シナリオを実行する。
- チュートリアルで利用するコマンドの挙動が変わった場合は、同じリリースで更新する。
- 定期的に全チュートリアルを再実行し、サービス側の仕様変更も検出する。
- 非互換変更では、リリース前にアップグレード手順を実環境で確認する。
- 未リリースのコマンドをチュートリアルへ掲載しない。
